Why quitting could take six seconds

Sprite Terminal stopped its terminal I/O thread, then waited for the child process to finish while keeping the terminal descriptors open. A child exiting after a hangup could remain blocked until those descriptors closed. The six-second safety deadline eventually closed them, releasing the child. This created an avoidable wait even after the process scanner reported no live session jobs.

The measured result

ScenarioBeforeAfter
Shell prints during its HUP exit handler6.043 seconds0.003 seconds
Three terminal VSVim panes, second Cmd+Q to process exit6.053 seconds0.020 seconds
Three native VSVim panes, second Cmd+Q to process exitVariable: 0.080–3.056 seconds0.081 seconds

These are local macOS samples, not latency guarantees. The native run did not reproduce the full six-second delay. The terminal run and the minimal shell regression did. Each GUI probe verified that the first Cmd+Q asked about three running Neovim programs and the second confirmed the warning.

The change

After the I/O pump reports that it has stopped, Sprite joins that thread and releases both the worker’s terminal master and the duplicate used for foreground queries. It then waits for child-exit reporting and process cleanup. Process identities are retained independently of the terminal descriptors, so surviving ordinary session jobs still receive the existing HUP, TERM and KILL escalation. The two-, three- and six-second deadlines are unchanged.

Before: signal jobs → stop I/O → wait for child exit → deadline → close terminal
After:  signal jobs → stop I/O → close terminal → child exit → finish cleanup

Evidence and reproduction

The regression uses the public TerminalSession API to run this shell, wait for READY, and request shutdown:

trap 'printf CLOSING; exit 0' HUP
printf READY
while :; do sleep 1; done

It failed before the fix at 6.04 seconds. With the fix, it finishes promptly and reports the HUP handler’s normal exit code. Run it with:

cargo test -p sprite-term --test lifecycle   shutdown_does_not_wait_for_the_deadline_when_a_child_prints_while_exiting

The throwaway desktop build dispatched Ctrl+Shift+D, Ctrl+Shift+E, Cmd+Q, Cmd+Q through the real window event dispatcher. It opened three real VSVim panes and recorded shutdown tracing. This exercised rendering, workspace confirmation, real PTYs, cleanup threads and app exit, but did not inject physical AppKit keyboard events. Probe modifications were removed from the production diff.

Representative trace:

Before: pump_stopped_observed → scope empty → worker_pending_settlement
        give_up at about 6010 ms → child_wait_returned
After:  pump_stopped_observed → pty_released at about 1 ms
        child_exit_observed → worker_settled at about 1 ms

No duplicate Sprite Terminal process or serial pane-cleanup wait was observed. The baseline did leave one detached scratch Neovim alive during sampling; it was explicitly cleaned up. Fixed desktop runs left no scratch Neovim processes.

Validation boundaries

Validation covers the terminal library’s unit tests; lifecycle, event backpressure, session I/O and session output integrations; and workspace quit-flow tests. The lifecycle tests include children that ignore HUP/TERM and still require the three-second KILL step, natural exits with retained descendants, and output-tail publication. Linux desktop behavior and physical keyboard delivery are not established by the local macOS probes.

Raw local evidence is in /tmp/sprite-quit-investigation/: minimal-red.log, minimal-green.log, terminal-timed.log, terminal-fixed.log, native-fixed.log, and the test summaries. These temporary files are not part of the repository.
