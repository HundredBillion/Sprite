# Run blocking Surface writes and pane cleanup on dedicated threads

Surface events were written with blocking `write_all` on the GPUI thread under a two-second send timeout (ADR 0018), so one plugin that stopped reading froze rendering and input for every Pane in the Sprite Window. Each live Surface connection now owns one writer thread and a pending queue that admits an event only while fewer than 4 MiB are already waiting, so one large event (a big paste) behaves as before while a stalled reader stays bounded; the GPUI thread only enqueues and never blocks. Refusal at the bound, a write timeout or a write failure marks the connection dead and shuts the socket down, which is the outcome a stalled peer already had, without the freeze. One queue per connection preserves the existing ordering guarantees (`opened` first, contiguous batches and gestures), and a graceful close lets the writer send what is queued, including `closed`. Surface connections are capped at sixty-four, so so are writer threads. Rejected: a non-blocking socket flushed from the UI thread (the UI thread still performs I/O and needs a readiness hook GPUI does not offer) and a shorter timeout (shortens the freeze without removing it).

ADR 0024 kept blocking pane cleanup — HUP/TERM/KILL escalation and joins of up to several seconds — on GPUI's background executor. On Linux that executor is a fixed pool of `available_parallelism()` threads, so closing or quitting with as many busy Panes as cores starved all other background work. Each pane cleanup now runs on its own short-lived named thread and signals completion to the Sprite Window's existing pending-cleanup tracking, which still owns the lifetime rule of ADR 0024. Cleanups stay concurrent, so quit time does not multiply with Pane count. Rejected: one serial cleanup thread (quit would take the sum of per-pane deadlines) and a small fixed pool (more code to own for no observed need). This supersedes the earlier audits' "no new I/O helper thread" constraint for these two cases only.
