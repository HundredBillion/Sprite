Sprite Terminal · agent communication between panes

One agent.
Many panes.
Explicit permission.

An agent running in one pane can read or act on another pane by asking Sprite. Sprite authenticates the request, checks the owner's grant, and routes it to the pane or its Terminal Session.

Implemented on the issue 106 branchOffline, standalone architecture explainer
01

Sprite is the intermediary.

The agent chooses what to do. Sprite supplies access to terminal context and authorized operations. The target can be an existing human pane, a new agent pane, or a pane running in a background tab.

An authorized request, from intent to effect
Caller · outside Sprite's processAgent in Pane A

Invokes the sprite CLI or speaks the public control protocol.

→
Local transportPrivate Unix socket

A separate grant key authenticates the connection. No TCP listener.

→
Sprite · UI threadWorkspace

Claims the request, checks current rights and scope, then dispatches by pane identity.

→
Sprite · addressed targetPane B / Session B

Layout changes use the pane tree. Text and input use the session worker.

← Owned JSON result, terminal text, or an explicit refusal returns to the caller.

The socket is handled on connection threads. A bounded lane crosses to the UI thread. Terminal parsing and encoding stay on the Terminal Session's worker. The CLI is a separate client process; it does not manipulate GPUI or a PTY directly.

What “communication” means here: reading another pane's terminal output, managing its layout and lifecycle, or sending separately authorized terminal input. Sprite does not provide an agent chat inbox, an LLM runtime, or a durable agent-to-agent message bus. The agents supply their own coordination logic.

02

Three channels, separate authority.

They reuse the same protected local transport implementation. Their credentials, grammars, and responsibilities remain separate.

OBSERVATION

Read pane context

sprite panes snapshot collects owned terminal snapshots from panes in the same window. Its broker cannot express pane mutations.

The window's existing observation credential is shared with launched sessions. It can request an access prompt, but cannot approve one.

PANE CONTROL

Manage addressed panes

sprite panes … --access FILE uses a fresh owner-approved grant. Each grant has its own endpoint and key.

Read is included. Management and terminal input are separate permissions. Control reads authorize on the UI thread, then reuse the observation broker.

SURFACE CHANNEL

Draw native UI in a pane

sprite surface open opens an element, grid, or list Surface inside a pane. It supports native UI updates and events.

A Surface is hosted content, not a new pane type. Pane control does not grant synthetic Surface input or ownership of its native document.

Choose a path, then step through the code that handles it. This walkthrough illustrates the implementation; it does not contact a running Sprite window.

CLI process

Load the grant descriptor

The CLI reads a private access file containing the window incarnation, grant ID, socket path and bearer key. The request names a pane using its window and local pane identity.

The agent holds a capability, not a live pane handle.

Legacy snapshot difference: panes snapshot goes from its authenticated endpoint to the observation broker, using pane membership already published by the Workspace. It does not queue a new UI-thread authorization request for each read.

04

A grant is permission to ask.

The owner approves all existing and future panes in one window, or a fixed set. A fixed grant also includes panes created through that grant. Permission is checked again when an operation executes.

Explore a control grant

Illustrative policy outcomes
Addressed target
Expected permission decision
Read terminal contextallowed
Rename, move, focus or resizeallowed
Create a configured-shell paneallowed
Send terminal text or a keydenied
Close the addressed paneconfirmation_required

Input needs its own permission. Management can start a configured shell, but cannot type into it.

This explorer isolates grant checks for an existing terminal pane, with creation beside that pane. It assumes valid requests, available capacity and no conflicting human drag. Real operations also check lifecycle, content support and resource admission.

Revocation is a live check. An operation still waiting in the UI queue cannot use revoked rights. A human confirmation rechecks its original grant and target. Revocation cannot undo an operation that already committed. This capability model does not sandbox hostile processes running as the same OS user.

05

A concrete agent workflow.

  1. Ask the person for access.

    The CLI uses the containing window's observation channel to request a grant. Sprite displays the requested scope and rights. Only the person's Allow action approves it.

  2. Receive a separate capability.

    Approval creates a grant endpoint and returns a descriptor. The CLI saves it as a private file; stdout does not print the key. The credential is not automatically injected into new pane environments.

  3. Discover and read a target.

    List reveals authorized addresses and state. Read returns metadata and bounded terminal text, with completeness information. Terminal output is untrusted data, not an instruction to the agent.

  4. Act with the granted rights.

    Manage layout and lifecycle with --manage. To send text or keys, request --input too. Admission of input does not establish command execution or completion.

  5. Revoke when finished.

    The person uses Pane Access to revoke a grant or remove management/input rights. Re-enabling rights needs a fresh request and approval.

CLI · run inside the desired windowExample, not a live transcript
# Management and input are requested separately.
sprite panes access request \
  --all-panes --manage --input \
  --output /tmp/agent-access.json

# After the owner chooses Allow:
sprite panes list \
  --access /tmp/agent-access.json

# Use the full address returned by list.
sprite panes read \
  --access /tmp/agent-access.json \
  --pane WINDOW:7 --lines 100

sprite panes input \
  --access /tmp/agent-access.json \
  --pane WINDOW:7 --text 'echo hello'

sprite panes input \
  --access /tmp/agent-access.json \
  --pane WINDOW:7 --key enter

WINDOW:7 is a placeholder for a returned address. An input key is one key press. Remote key-release and hold events are unsupported.

What is on the wire?

Connect to the grant's Unix socket. Send the bearer key, a space, and one JSON document followed by a newline. The response is JSON with the same request ID. Unknown fields are rejected.

<key> {"protocol":"sprite-pane-control/1","id":"req-1",
 "window":"WINDOW","operation":{"op":"read","pane":"WINDOW:7","lines":100}}

{"protocol":"sprite-pane-control/1","id":"req-1",
 "outcome":"ok","result":{…}}

The request is shown wrapped for readability; the actual request occupies one line. IDs correlate responses, but are not durable replay or deduplication keys.

06

The details that keep it predictable.

16active grants per window
16connections per grant
16queued control operations per window
8 KiBauthenticated request-line limit

Claim before applying

The connection thread offers a request to a bounded lane. A full lane returns busy. If the caller abandons before the UI claims the request, the UI drops it without applying it.

If the UI has claimed it and the result cannot be recovered in time, the honest outcome is outcome_unknown. The client inspects state instead of automatically retrying a create, move, close or input operation.

Identity survives movement

A public pane address combines a random window incarnation and a pane ID that is never reused within that window. Moving a pane transfers its existing handle and session.

Sprite updates observation membership and resolves natural exits against the pane's current tab. Another window needs its own grant; moving sessions between windows is unsupported.

Busy close and unsafe input require a person.

A busy close returns confirmation_required, with a 30-second Confirm/Cancel prompt. Repeating the protocol request never confirms it. Unsafe text uses the terminal engine's conservative paste-safety classifier and also requires explicit approval. Input keys still need the separate input right.

Prompt buttons capture a unique identity, so an old button cannot approve a replacement request. Agent-driven focus and layout changes withdraw old human close confirmation. The addressed close uses the pane's foreground-job warning and normal cleanup, rather than permission to signal arbitrary host processes.

Accepted layout changes must survive redraw.

Resize updates a persistent split ratio, with the same logical-pixel allocation and minimum-size rules as human divider movement. It does not just send a terminal resize that the next layout overwrites. A side with no divider is explicitly unsupported. Background allocations take effect when shown; later window resizes still adjust the layout normally.

Agent create, move, focus, resize and close return busy while a human divider drag owns the layout. A pane label, a user-assigned Tab Name, and a child-provided Pane Title remain separate fields.

Reading a pane does not expose every native UI document.

A terminal pane can contain fill, dock and overlay Surfaces, with element, grid or list bodies. Pane control reports this presentation and can manage the containing pane. Read exposes underlying terminal text; native documents, editor buffers and raster content are explicitly unavailable through this channel.

Terminal input targets the terminal even when a Surface has keyboard focus. Native Surface updates and events remain on the independently authorized Surface Channel.

Cleanup and resource admission are bounded.

Agent creation refuses at 128 live panes or 16 unfinished pane cleanups per window; agent close refuses at 16 unfinished cleanups. Ordinary keyboard behavior remains available, and keyboard-created resources count toward subsequent agent admission.

Input payloads are limited to 4 KiB and labels to 256 bytes. Read history retains the existing 5,000-line cap and a single 500 ms broker deadline. A successful close reports layout removal and scheduled cleanup, not process-cleanup completion. The final pane's reply is sent before endpoint teardown while Sprite still waits for owned cleanup.
