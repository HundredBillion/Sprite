The problem

Sprite splits panes evenly and leaves them that way. A split is born at a ratio of 0.5 and nothing in the product can ever change it.

PaneTree stores a ratio per split node but exposes no operation that reads or writes one. And the divider is not an object at all — it is a one-pixel gap, produced by shrinking every pane by DIVIDER_PX and letting the container's background show through.

So someone who wants an editor twice the width of a log tail cannot have it. Every terminal Sprite is measured against — Ghostty, kitty, WezTerm, tmux — lets a divider be dragged.

“As a mouse user, I want to focus and resize panes by clicking and dragging, so that layout adjustments are direct.” — Phase 1 PRD, story 15. Clicking to focus landed in Checkpoint 3. Dragging to resize did not.

The gesture

Hover

↔ resize cursor

A 7 px strip over the 1 px gap. One pixel cannot be hit with a mouse.

Drag

continuous

Both panes follow the pointer. Neither may go below 120 px — the divider simply stops.

Double-click

→ 50 / 50

Undoes an over-enthusiastic drag in one gesture.

Keyboard

Ctrl+Shift+Alt + ←↑↓→

Moves the focused pane's boundary on that side by 20 px, through the same clamp.

Naming a divider

A drag needs a name for the boundary it grabbed that stays valid for the length of the gesture. The tree has no name for a split node, so one has to be chosen. Three were considered.

Rejected

Mint a DividerId

Stable and never reused, matching the file's identity rules — but it changes three split signatures and puts a second identity type beside the one the observation schema already exposes. More vocabulary than the problem needs.

Rejected

A tree path

A bit-path from the root needs no new type, but it is valid only until the tree changes shape — and a stale path resolves silently to a different divider rather than to nothing.

Chosen

The pane on its low side

A divider is “the boundary on side D of pane P” — reusing PaneId and the Direction focus navigation already uses. No new identity type, and the same address serves the drag, the double-click, and the keyboard nudge.

The rule

The boundary on the right of pane P is the nearest ancestor split of horizontal orientation whose subtree containing P is that split's first child. Where P's subtree is the second child, that split is P's left boundary.

The rule matters most where a naive one fails. Take [[A|B] | C]. The nearest horizontal ancestor of B is the A|B split — but the boundary to B's right is the root's. Walking up from B, the A|B split is skipped because B is its second child, and the walk lands on the root.

And for enumeration, each split names itself by the last leaf of its first subtree — B, in that example. The walk up from a last leaf skips every intermediate split of matching orientation, because a last leaf is by construction in each of their second children.

Where the work lives

The split between the three layers is the point. GPUI event handlers have no test seam — anything inside one is verified only by hand — so nothing that can be wrong is allowed to live there.

pane_tree.rs pure · normalised · fully testable

Two operations, no pixels, no GPUI:

  • dividers() → Vec<Divider>one per split: naming pane, direction, orientation, current ratio, the split's own area. Ratio and area both, because the area converts pixels to a ratio and the ratio seeds a drag from where it was grabbed.
  • set_divider_ratio(pane, direction, ratio) → boolresolves by the rule above; reports whether a divider was found.

Neither touches pane identity, focus, or session ownership — the property Phase 1 already states about resize, and one the tree's tests already know how to assert.

workspace.rs pixels · free functions · testable without a window

divider_ratio(area_origin_px, area_extent_px, pointer_px, floor_px) → f32

Maps a pointer position to a ratio and clamps it so neither side falls below the floor. A free function, not a method on the drag state, precisely so it can be tested. The drag and the keyboard nudge both go through it, so the two cannot disagree about where the floor is.

split_area's existing 0.05..=0.95 clamp stays as the tree's own safety net for its invariants — it is not the product's minimum size.

GPUI handlers no test seam · verified by hand · kept trivial
Hit strips, the drag overlay, and the press/release bookkeeping. Every decision they make is a call into one of the two layers above.

Three mechanics worth stating

The drag needs an overlay

GPUI's on_mouse_move fires only while its own hitbox is hovered, so a 7 px strip loses the pointer the moment the pointer outruns it — the common case in a fast drag. While a drag is live, one occluding overlay across the whole pane area carries the move and release listeners.

It also guarantees a gesture begun on a divider cannot become a text selection in the pane underneath: one gesture, one meaning.

The grab keeps its offset

A press records where within the strip it landed, so the divider does not jump to centre itself under the pointer on the first move.

A release anywhere ends the drag. A move that arrives with no button held ends it too — which is how a release lost outside the window is recovered.

Alt is relaxed for arrows only

workspace_action rejects any keystroke carrying alt, so alt-modified keys reach the child. Only Ctrl+Shift+Alt + arrow is carved out.

A pane already against the tab's edge does nothing. Growing a pane by moving its opposite boundary was rejected: it makes one key mean two motions depending on where the pane sits.

What needs no work

Child resize

A pane's TerminalView is told its allocation every render, and synchronise_size sends a resize only when the cell count changes. A continuous drag therefore produces at most one resize per column or row crossed — not one per frame.

Observation

Pane rectangles are published from render on every frame, so a resized layout reaches observation clients with no new plumbing.

User stories

  1. 01

    As a mouse user, I want a resize cursor when I hover a divider, so that I can see the boundary is draggable before I press.

  2. 02

    As a mouse user, I want to drag a divider and have both panes follow the pointer, so that adjusting a layout is direct rather than a matter of configuration.

  3. 03

    As a mouse user, I want a divider I have grabbed to keep following the pointer when the pointer moves faster than it or leaves it, so that a quick drag does not silently stop halfway.

  4. 04

    As a mouse user, I want a drag that starts on a divider never to select text in the pane underneath, so that one gesture has one meaning.

  5. 05

    As a mouse user, I want to double-click a divider to return that split to even, so that undoing an over-enthusiastic drag takes one gesture.

  6. 06

    As a keyboard user, I want Ctrl+Shift+Alt and an arrow to move the focused pane's boundary on that side, so that resizing does not require a mouse.

  7. 07

    As a shell user, I want a resized pane's child to learn its new dimensions, so that full-screen programs redraw at the size they are actually given.

  8. 08

    As a shell user, I want resizing a pane never to disturb any pane's session, scrollback, or focus, so that layout work is safe during real work.

  9. 09

    As a terminal user, I want neither side of a split to shrink below a usable size, so that a pane cannot be dragged into something visible but unusable.

Out of scope

Persisting ratios across restarts

Sprite persists no layout today, and a resize is not the change that should introduce a session store.

Dragging a pane to a new position

Or any layout gesture beyond moving a boundary that already exists.

Resizing across tabs or windows

A divider belongs to one tab's tree.

Configurable bindings, strip width, or minimum size

Configuration is a Phase 1 subsystem in its own right; this change adds nothing to its schema.

Snapping to whole cells

The drag is continuous. A pane keeps the partial cell of padding it already keeps at every other edge.
